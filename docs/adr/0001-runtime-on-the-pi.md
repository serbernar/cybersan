# ADR 0001 — Що саме виконується на Raspberry Pi

**Дата:** 2026-09-05
**Статус:** прийнято

## Контекст

Прототип надихнув [cyberpandino/cluster](https://github.com/cyberpandino/cluster) —
робоча цифрова панель приладів на Pi 4. Там на машині виконується Node.js,
Vite dev server і Electron. Автори самі оцінюють це приблизно в 500 МБ RAM і
приблизно 30 секунд до появи інтерфейсу.

Наша Pi 4B має 4 ГБ RAM, Debian 13 і сесію labwc/Wayland. Nissan X-Trail T30 —
не заміна щитка приладів, а окремий пристрій у центральній консолі.

## Рішення

1. **HUD збирається на робочій машині**, на Pi їде тільки статичний `dist/`.
2. **Бекенд — Python 3 + asyncio (aiohttp)**, він же роздає цей `dist/`.
3. **Оболонка — Chromium `--kiosk --app=`**, без Electron.
4. **Контракт даних живе в одному файлі** (`packages/protocol/default-state.json`
   + типи), який читають обидві сторони.

## Наслідки

Добре:

- На машині немає Node, npm, Electron і жодного кроку збірки. Оновлення — це `rsync`.
- Один origin: HTTP і WebSocket з одного порту, без CORS і без другого сервера.
- Python уже є в системі, а майбутні джерела даних (`python-obd`, `gpiozero`, `gpsd`)
  — це той самий стек.
- Менше RAM і швидший старт, бо немає другого рантайму.

Погано або ризиковано:

- HUD не можна поправити «на місці» на самій машині — потрібен деплой з ноутбука.
- Python повільніший за Node на високочастотному парсингу; для 10 Гц оновлень
  це не має значення, але для CAN-снифінгу доведеться перевіряти окремо.
- Chromium kiosk не дає нам контролю над splash до моменту першого кадру;
  екранна заставка — це вже частина застосунку, а не Plymouth.

## Альтернативи, які відхилено

- **Electron** — другий рантайм заради повного екрана, який дає той самий Chromium.
- **Qt/QML або Flutter Linux** — швидші й «правильніші» для автомобільного UI,
  але на порядок повільніші в ітераціях і без готового вебстека для верстки.
- **Node-бекенд** — довелося б ставити на Pi ще один рантайм лише заради сервера,
  тоді як Python там уже стоїть і має бібліотеки для OBD/GPIO.
